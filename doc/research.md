# Research: можно ли улучшить сжатие fb2opt

- Дата: 2026-09-11
- Текущий пайплайн (из кода): PNG `ect -9` → PIL exact-варианты (gray/palette/JPEG→PNG, гейт `CLOSE_RATIO=1.2`, `_packed_cost` = base64+zlib-9) → JPEG `ect -9 -strip -progressive` → XML-минификация → ZIP `zipfile DEFLATED-9` + `ect -9 -zip` (комменты восстанавливаются). Дедупликации одинаковых `<binary>` нет, второго оптимизатора кроме `ect` нет, JPEG-финиша кроме `ect` нет.
- Источники: бенчмарк oxipng#700 (oxipng 9.1.5 / zopfli 1.0.3 / ect 0.9.5): total saved MB — oxipng 66.14, oxipng-Z 66.49, zopflipng 59.85, **ect 61.92, oxipng+ect --reuse 67.05** (лучший результат за 483с против 257с у ect); таблица ECT vs zopfli (ECT-9 жмёт сильнее zopfli-i30 и в ~2 раза быстрее); jpegoptim vs jpegtran vs mozjpeg (mozjpeg-jpegtran ≈1.7× времени за маржинальные проценты; режимы: lossless jpegtran / lossy cjpeg); advzip man (libdeflate +5–10% к zlib, zopfli-insane, LZMA -N несовместим с ридерами).
- Вывод короткий: **да, выжать ещё можно, но дёшево — только 1–3% поверх текущего на PNG-тяжёлых книгах и до десятков % на книгах с дубликатами картинок.** Контейнер (ZIP) уже почти у потолка: ECT-9 на уровне/лучше zopfli, пережатие через advzip даст десятые доли процента.

## Вариант 1: цепочка PNG `oxipng → ect --reuse`

Суть: сначала `oxipng -o4..6` (лучшие reductions/фильтры/палитры), затем `ect -9 --reuse` только пережмёт IDAT кастомным Zopfli, не трогая найденные трансформации. Сейчас идёт только `ect -9` (свои эвристики фильтров слабее oxipng на части классов: `reductions 6.13 vs 6.64`, `content-palettes 2.59 vs 4.31` в пользу связки).

| Критерий | Оценка |
|----------|--------|
| Сложность | 2–3 дня (детект `oxipng`, цепочка в `_ect_squeeze`/`_squeeze_candidate`, гейт по `ECT_FAST_BYTES`, тесты с моком, доки) |
| Риски | Низкие: оба инструмента lossless попиксельно; `pixel-identity` проверка уже есть и ловит регресс. Риск — время (связка ~1.9× от ect) и новая зависимость (опциональная, fallback на чистый ect) |
| Плюсы | Лучший известный результат по бенчмаркам (+5.1MB к ect на корпусе ≈ +8% доп. экономии PNG-части; на `.fb2.zip` реально +1–3% для PNG-тяжёлых книг); включается только когда `oxipng` найден |
| Минусы | −2× время на PNG; выигрыш почти нулевой на фото-JPEG книгах и на уже оптимальных PNG; нужен `--reuse`-совместимый ect |
| Влияние на архитектуру | Минимальное: новый опциональный бэкенд рядом с `run_tool(["ect",...])`, решение «держать packed-smaller» без изменений |

## Вариант 2: JPEG-финиш `mozjpeg jpegtran -optimize -progressive`

Суть: после `ect -9 -strip -progressive` прогонять `jpegtran -optimize -progressive` (mozjpeg-сборка: оптимизация scan-скриптов в духе jpgcrush + trellis-квантование не трогает лосслесс-режим, только энтропию). Ожидание честное: маржинальные проценты (по SO-замерам mozjpeg-lossless ≈ +1–2% к байтам JPEG за ~1.7× времени), но на фотокнигах JPEG — 70–90% веса, и даже 1% виден.

| Критерий | Оценка |
|----------|--------|
| Сложность | 1–2 дня (детект `jpegtran`, один вызов в `_ect_squeeze` для `jpg`, `_looks_complete` + `_packed_cost` гейт уже есть, тесты) |
| Риски | Низко-средние: прогрессивность уже принята проектом (README caveat про старые читалки); mozjpeg-прогрессив иногда кладёт больше сканов — проверить открываемость на тестовой Pam-книге; fallback на ect-вариант при отсутствии бинаря |
| Плюсы | Дешёвый доп. выигрыш именно там, где PNG-цепочка бессильна (фото); ускорение декодирования не страдает; опциональная зависимость |
| Минусы | Выигрыш маленький и не гарантирован на каждом файле (держать только строго меньший); +1 внешняя зависимость; на малых JPEG (<`ECT_FAST_BYTES`) может не окупаться по времени |
| Влияние на архитектуру | Минимальное: ещё одна ступень в `_ect_squeeze`, инвариант «packed-smaller + `_looks_complete`» без изменений |

## Вариант 3: дедупликация одинаковых `<binary>` + нормализация XML

Суть: в `optimize_fb2_payload` считать `sha256(raw)` каждого декодированного блока; полные дубликаты (частый случай: обложка + её же превью, повторяющиеся виньетки/заставки) хранить один раз, остальные `<binary>`-блоки заменять... вот здесь развилка: FB2 ссылается по `xlink:href="#id"`, поэтому правильно — оставить один блок и переписать ссылки дубликатов на surviving id (а не удалять блоки, иначе сломаются ссылки). Бонусом: детерминированный порядок атрибутов `id/content-type`, единый `content-type` после кроссоверов (уже частично есть). На книгах без дубликатов выигрыш 0; на книгах с N повторами — до `(N-1)×(base64 тела)` минус deflate-окно (дефлятор ZIP видит повторы только в пределах 32KB, а дубликаты обычно в мегабайтах друг от друга — окно их не ловит, так что выигрыш почти полный).

| Критерий | Оценка |
|----------|--------|
| Сложность | 4–7 дней (хеширование в пайплайне, карта `hash→surviving_id`, переписывание `xlink:href`, подсчёт `stats`/`marks` для удалённых тел, тесты: дубли/ссылки/круговая ссылка/разные id один хэш, доки) |
| Риски | Средние: единственный вариант, трогающий семантику документа (ссылки), а не только байты. Нужны инвариантные тесты «все `href` резолвятся», «число уникальных картинок сохранено», «валидность по FB2-схеме». Откат простой: флаг `--no-dedup` |
| Плюсы | Потенциально самый большой выигрыш из трёх (0% обычно, 10–30% на книгах с дубликатами); чистый Python, без новых зависимостей; ускоряет и последующие `ect`/ZIP-проходы (меньше данных) |
| Минусы | Выигрыш бимодален (часто ноль); усложняет учёт `png_saved/jpg_saved` по типам и `program-used` штампы lossy (дубликат штампованного изображения делит судьбу оригинала — решить правилом) |
| Влияние на архитектуру | Умеренное: новый проход между декодированием и `optimize_images`, плюс переписывание ссылок в скелете; `_Image`/статистика расширяются полем `dup_of` |

## Рекомендация

Порядок внедрения по соотношению выигрыш/риск: **3 → 1 → 2**. Дедупликация — единственная с шансом на двузначные проценты и без зависимостей (начать с dry-run счётчика «сколько бы сэкономили», затем включать по умолчанию с `--no-dedup`). PNG-цепочка и JPEG-финиш — опциональные ступени за детектом бинарей, каждая держится правилом «только строго packed-smaller + pixel-identity», поэтому безопасны для дефолта.

| Лимиты 1000px/150КБ/80КБ | Отклонить как принцип | Абсолютные капы режут качество независимо от цены байта; 1920px обоснован экранами. Single-export уже делается (один финальный энкод) |

### XML-метаданные (publish-info, src-title-info, history, keywords, stylesheet): отклонить целиком
- Ломает контракт lossless-оптимизатора (сохранение, валидность, «не трогает»).
- Удаление `<program-used>` уничтожит собственный храповик `--lossy` — самоповреждение.
- Удаление stylesheet/history меняет рендеринг и ломает библиотечные менеджеры; экономия — сотни байт, почти в ноль после дефляции.
- Regex-подход — то, чего проект избегает осознанно.

## Разбор пяти предложений (2026-09-11)

### 1. Дедупликация одинаковых изображений — реализовать, но с валидацией
Замер на коллекции: 0/250 книг с точными дубликатами, так что ожидание ≈0 на текущем корпусе; но как механизм — корректно реализуемо. Главная опасность не в поиске дублей (sha256 raw), а в переписывании ссылок: пропущенная форма `xlink:href` (другое квотирование, неймспейс) = пропавшая картинка. Кодеру: ключ — sha256 декодированных байтов; выживает первый блок; ссылки dup-id → surviving-id переписывать до удаления блоков; после — проверка «все href резолвятся», иначе откат книги; учёт в `stats`, взаимодействие со штампами lossy (дубликат делит судьбу оригинала); флаг `--no-dedup` для отката. Оценка: 4–7 дней, средний риск.

### 2. Нетипичные вложения (TIFF, GIF) — делать, в оба режима, с гардами
Однокадровый TIFF→PNG и неанимированный GIF→PNG доказуемо попиксельны (PNG lossless), значит проходят дефолтный инвариант; плюс старые ридеры TIFF вообще не читают — конверсия реально повышает читаемость. Кодеру: расширить `GENERIC_SAFE_FORMATS` ветку: TIFF только при `n_frames==1` и без orientation/exif (иначе ориентация перевернёт показ), GIF только неанимированный (`is_animated` False); каждый кандидат через `_pixels_equal` + packed-гейт как сейчас. Анимированный GIF и многостраничный TIFF — всегда keep (иначе потеря кадров/страниц). Оценка: 1–2 дня, низкий риск. Единственное из пяти с пользой для дефолта.

### 3. Кэш вложений между книгами — сначала замер, потом решение
Ключ обязан включать все параметры, влияющие на выход (sha256 + kind + lossy-target + наличие ect/oxipng...), иначе lossy-результат утечёт в lossless-контекст. Потокобезопасность (лок), рост RAM (кэш держит оптимизированные байты — конфликт с лимитами памяти), дисковый кэш между запусками — протухание при смене версий инструментов, инвалидация, управление размером. Кодеру: этап 1 (~0.5 дня) — только счётчик хитов по sha256 через батч в лог, без кэширования; этап 2 — in-memory кэш на батч, только если хиты измерены. Постоянный дисковый кэш — отклонить до измерений (сложность/протухание/диск против недоказанной выгоды; внутрикнижных дублей 0/250).

### 4. Маркер lossy нулевым байтом в конце файла — отклонить
(a) Математика в предложении перевёрнута: +1 байт растит base64 только при n%3==0, т.е. бесплатно в ~67% случаев, а не 25%. (b) Критично: `ect` при следующем прожатии нормализует файл и байт отвалится — маркер потерян молча, защита от храповика исчезает, качество начнёт лесенкой вниз (ровно то, от чего штамп защищает). (c) «Любой парсер проигнорирует» неверно для строгих/дешёвых декодеров — а это как раз старые ридеры, ради которых всё затевалось; `pngcheck`-строгие валидаторы ругаются. (d) Ломает инвариант `_looks_complete` и честность «байты = картинка». Выигрыш — десятки байт на книгу. XML-токен в `program-used` остаётся правильным решением.

### 5. Выкидывание мета-тегов в lossy — только явным флагом, не в комплекте
Связывать удаление метаданных с `--lossy` — ошибка проектирования: это ортогональные оси (пользователь может хотеть lossy-картинки, но curated-метаданные). Если делать: отдельный `--strip-meta` (дефолт ВЫКЛ), сохранять `id` + `program-used`-токен + genre/lang/title/author, печатать что удалено, тесты на XSD-валидность. Экономия — десятые доли процента (метаданные дефлируются почти в ноль), stylesheet трогать опаснее всего (часть ридеров его уважает). Приоритет низкий; в дефолт и в `--lossy` молча — никогда.

## Второй раунд возражений (2026-09-11)

### 1. MD5 + размер для дублей и кэша — принимается
MD5 вдвое быстрее SHA-256, а стойкость к коллизиям здесь не нужна: случайная коллизия разных картинок невозможна практически, а злонамеренную (две разные картинки с одним MD5 в одной книге) некому и незачем подсовывать — автор враждебного FB2 и так кладёт туда любые картинки. Размер первым — дешёвый префильтр до хеширования. Кодеру: ключ `md5`, сравнение `(len, digest)`; оговорка — FIPS-сборки Python блокируют MD5 без `usedforsecurity=False` (ловить исключение → fallback на sha256). Для кэша требование не снято: в ключ входят настройки (kind, lossy-target, наличие ect/oxipng), иначе утечка между режимами.

### 2. Нулевой байт «после lossy перед base64» — всё равно отклонить
Позиция в нашем пайплайне не при чём: проблема — время жизни маркера, а не место вставки. Любая будущая нормализация байтов (повторный прогон fb2opt, `ect`, Calibre, Pillow round-trip — Pillow дропает трейлинг при `save`) тихо съест байт, и храповик посыпется на следующем `--lossy`. Аргумент «плохие декодеры всё равно ошибутся» — ложная эквивалентность: валидный файл работает везде по определению валидности; мусор после IEND/FFD9 превращает его в файл, работающий по снисходительности декодера. Плюс ломает `_looks_complete`-инвариант и pngcheck-чистоту. Спасаемая часть идеи: маркер в валидном носителе (PNG `tEXt` пережил бы и ect, и Pillow — проект чанки и так хранит), но для JPEG при `ect -strip` валидного носителя нет → асимметрия PNG/JPEG ради десятков байт. XML-токен остаётся решением.

### 3. Чистка тегов как часть lossy с disclosure в README — принимается с условиями
Довод «читателю техтеги не нужны, библиотекарь — наша программа» почти верен, кроме одного тега: `program-used` нужен самой программе (храповик), `id` — внешним системам (признаёт и сам источник). Уступка: отдельная ось/флаг ради десятков байт — это sprawl флагов; документированная связка «lossy = кардинальное пожатие» — связная продуктовая история, surprise снимается README. Условия кодеру: чистка только под `--lossy`, сохранять `id` + токен + reader-visible набор (genre/lang/title/author), удалённое печатать в stderr, тесты на XSD-валидность, предупреждение о бэкапе (операция необратима). Связку «lossy-пиксели, но curated-мета» теряем осознанно.

## Третий раунд: байт-маркер (конструкция) + чистка тегов по XSD (2026-09-11)

### 2а. Трейлинг-байт: проверено, конструкция для кодера
Замер: Pillow открывает и грузит PNG/JPEG с лишним байтом, пиксели идентичны; `ect -9` rc=0, байт нормализует, выход валиден. Вывод: механизм реализуем, но переживает он только НАШ пайплайн — любой внешний нормализатор (повторный чужой прогон, Calibre, Pillow-`save`) байт съест. Поэтому ядро конструкции — не «куда приделать», а «нести маркер в памяти и re-attach при сборке в ОБОИХ режимах»:
- Формат: один байт `clamp(round(target*100),1,100)` (0 не пишем никогда). Гранулярность таргета сохраняется.
- `_split_trail(raw, kind)`: только если `raw[:-1]` кончается строгим трейлером (IEND/FFD9) И последний байт 1..100 → `(body, byte/100)`, иначе `(raw, None)`. Природный мусор с нулём на конце → не маркер; мусор с концом 1..100 → ложноположительный, но в безопасную сторону (консервативный пропуск lossy).
- `_Image.trail: float|None` (default — старые конструкторы целы). Декод: сплит; все оптимизаторы работают с чистыми байтами; `_looks_complete`/strict-endswith не трогаем.
- Сборка: win → trail=target; иначе нести carried (байт старше токена; токен — fallback для старых книг). Keep-путь (`final==raw` + trail unchanged) оставляет `orig_body` байт-в-байт.
- Default-режим тоже re-attach при перезаписи, иначе дефолтный прогон тихо снимет все метки.
- Миграция: ридеры токенов/legacy-атрибутов остаются (совместимость назад), писатели уходят (`_write_lossy_token`, `_set_lossy_mark`, `_render_lossy_token`, `_upsert_program_used` — удалить; `_strip_*` остаются как чистка старого мусора; `marks` становится освобождёнными байтами, ≥0). Бонус: отпадает fallback «штамп в теги без document-info» — байт приделывается всегда.
- Остаточные риски честно: внешние нормализаторы (паритет с убиваемым конвертерами токеном), pngcheck-строгие валидаторы, base64 +4 при len%3==0, дешёвые декодеры нетестированы (та же оговорка, что у progressive JPEG — проверить одну книгу).
- Тесты кодеру переписать: TestLossyMarker/TestReopenedAndWrapper (токен → трейлинг-байт в декодированном binary), fallback-тест (удалить/конвертировать), инвариант «дефолт не снимает метки».

### 3а. Чистка тегов: сверено с XSD (gribuser/fb2, FictionBook.xsd) — только delete-list
Whitelist («оставить список, остальное снести») опасен: пропустишь один обязательный элемент — невалид. Blacklist по minOccurs=0 — безопасен. Находка: предложение удалять `document-info/date` и всех `document-info/author` ЛОМАЕТ валидность — по XSD `date` ровно 1 (без minOccurs), `author` 1..n, `version` и `id` ровно 1. Проверка кодеру — валидировать выход тем же XSD.
- DELETE (схемно необязательное, невидимое): `publish-info` целиком; `src-title-info` целиком (⚠ теряется оригинал-название); `custom-info` всё; `output`*; `document-info/{src-url,src-ocr,history,program-used}` (program-used — только в эру байт-маркеров!); `document-info/publisher`*; лишние `document-info/author` (первый целиком оставить); `title-info/{keywords,date,translator}`; `home-page/email/id` внутри любых `author` (ветки XSD требуют first+last либо nickname — их не трогать); корневой `stylesheet`* (⚠ часть ридеров применяет).
- KEEP ВСЕГДА: `title-info/{genre,author≥1,book-title,annotation,coverpage,lang}` (+`sequence` — полки серий, +`src-lang` — 15 байт, не обеднеем); `document-info/{author≥1,date,id,version}`; всё в `body`; все `binary`.
- Правила кодеру: только `description` + корневой `stylesheet`, `body` священен; удаление preserving order (XSD — xs:sequence); на декодированном тексте в исходной кодировке; удалённое — в stderr; режим только под `--lossy` + секция README + варнинг о бэкапе.

## Замкнутый контур маркера (уточнение владельца, 2026-09-11)
Маркер существует только в готовой книге и в RAM (`_Image.trail: float`). Внешним программам (ect, oxipng, jpegtran, ffmpeg, Pillow-энкоды) отдаются всегда чистые байты:
- Decode (`decode_body` → `_split_trail`): отрезать, запомнить; дальше по пайплайну ходят только чистые байты — валидации (`_looks_complete`), сравнения (`_packed_cost`, `_pixels_equal`), метрика SSIM их не касаются и не меняются вообще.
- Keep-путь: чистые байты и trail без изменений → пишется исходный `orig_body` байт-в-байт (маркер цел автоматически).
- Rewrite-путь (lossless/probe/ect): к новым чистым байтам при сборке приделывается carried trail; lossy-win — новый target.
- Lossy-skip по метке: блок не трогается вообще (счётчик `marked`).
- `--extract`: отдавать байт-в-точь оригинал (с маркером), иначе repack тихо снимет защиту.
- Миграция токенов: токен → effective trail в RAM, в выход не пишется.
Тесты: мок `run_tool` с проверкой tmp-файлов (трейлинга нет ни в одном вызове); default-прогон по меченой книге (маркер на месте); повторный lossy тем же таргетом (skip); строже (reopen с новым значением).
