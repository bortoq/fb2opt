# Research: можно ли улучшить сжатие fb2opt

- Дата: 2026-09-11
- Текущий пайплайн (из кода): PNG `ect -9` → PIL exact-варианты (gray/palette/JPEG→PNG, гейт `CLOSE_RATIO=1.2`, `_packed_cost` = base64+zlib-9) → JPEG `ect -9 -strip -progressive` → XML-минификация → ZIP `zipfile DEFLATED-9` + `ect -9 -zip` (комменты восстанавливаются). Дедупликации одинаковых `<binary>` нет, второго оптимизатора кроме `ect` нет, JPEG-финиша кроме `ect` нет.
- Источники: бенчмарк oxipng#700 (oxipng 9.1.5 / zopfli 1.0.3 / ect 0.9.5): total saved MB — oxipng 66.14, oxipng-Z 66.49, zopflipng 59.85, **ect 61.92, oxipng+ect --reuse 67.05** (лучший результат за 483с против 257с у ect); таблица ECT vs zopfli (ECT-9 жмёт сильнее zopfli-i30 и в ~2 раза быстрее); jpegoptim vs jpegtran vs mozjpeg (mozjpeg-jpegtran ≈1.7× времени за маржинальные проценты; режимы: lossless jpegtran / lossy cjpeg); advzip man (libdeflate +5–10% к zlib, zopfli-insane, LZMA -N несовместим с ридерами).
- Вывод короткий: **да, выжать ещё можно, но дёшево — только 1–3% поверх текущего на PNG-тяжёлых книгах и до десятков % на книгах с дубликатами картинок.** Контейнер (ZIP) уже почти у потолка: ECT-9 на уровне/лучше zopfli, пережатие через advzip даст десятые доли процента.

## Вариант 1: цепочка PNG `oxipng → ect --reuse`

Суть: сначала `oxipng -o4..6` (лучшие reductions/фильтры/палитры), затем `ect -9 --reuse` только пережмёт IDAT кастомным Zopfli, не трогая найденные трансформации. Сейчас идёт только `ect -9` (свои эвристики фильтров слабее oxipng на части классов: `reductions 6.13 vs 6.64`, `content-palettes 2.59 vs 4.31` в пользу связки).

| Критерий | Оценка |
|----------|--------|
| Сложность | 2–3 дня (детект `oxipng`, цепочка в `_ect_squeeze`/`_squeeze_candidate`, гейт по `ECT_FAST_BYTES`, тесты с моком, доки) |
| Риски | Низкие: оба инструмента lossless попиксельно; `pixel-identity` проверка уже есть и ловит регресс. Риск — время (связка ~1.9× от ect) и новая зависимость (опциональная, fallback на чистый ect) |
| Плюсы | Лучший известный результат по бенчмаркам (+5.1MB к ect на корпусе ≈ +8% доп. экономии PNG-части; на `.fb2.zip` реально +1–3% для PNG-тяжёлых книг); включается только когда `oxipng` найден |
| Минусы | −2× время на PNG; выигрыш почти нулевой на фото-JPEG книгах и на уже оптимальных PNG; нужен `--reuse`-совместимый ect |
| Влияние на архитектуру | Минимальное: новый опциональный бэкенд рядом с `run_tool(["ect",...])`, решение «держать packed-smaller» без изменений |

## Вариант 2: JPEG-финиш `mozjpeg jpegtran -optimize -progressive`

Суть: после `ect -9 -strip -progressive` прогонять `jpegtran -optimize -progressive` (mozjpeg-сборка: оптимизация scan-скриптов в духе jpgcrush + trellis-квантование не трогает лосслесс-режим, только энтропию). Ожидание честное: маржинальные проценты (по SO-замерам mozjpeg-lossless ≈ +1–2% к байтам JPEG за ~1.7× времени), но на фотокнигах JPEG — 70–90% веса, и даже 1% виден.

| Критерий | Оценка |
|----------|--------|
| Сложность | 1–2 дня (детект `jpegtran`, один вызов в `_ect_squeeze` для `jpg`, `_looks_complete` + `_packed_cost` гейт уже есть, тесты) |
| Риски | Низко-средние: прогрессивность уже принята проектом (README caveat про старые читалки); mozjpeg-прогрессив иногда кладёт больше сканов — проверить открываемость на тестовой Pam-книге; fallback на ect-вариант при отсутствии бинаря |
| Плюсы | Дешёвый доп. выигрыш именно там, где PNG-цепочка бессильна (фото); ускорение декодирования не страдает; опциональная зависимость |
| Минусы | Выигрыш маленький и не гарантирован на каждом файле (держать только строго меньший); +1 внешняя зависимость; на малых JPEG (<`ECT_FAST_BYTES`) может не окупаться по времени |
| Влияние на архитектуру | Минимальное: ещё одна ступень в `_ect_squeeze`, инвариант «packed-smaller + `_looks_complete`» без изменений |

## Вариант 3: дедупликация одинаковых `<binary>` + нормализация XML

Суть: в `optimize_fb2_payload` считать `sha256(raw)` каждого декодированного блока; полные дубликаты (частый случай: обложка + её же превью, повторяющиеся виньетки/заставки) хранить один раз, остальные `<binary>`-блоки заменять... вот здесь развилка: FB2 ссылается по `xlink:href="#id"`, поэтому правильно — оставить один блок и переписать ссылки дубликатов на surviving id (а не удалять блоки, иначе сломаются ссылки). Бонусом: детерминированный порядок атрибутов `id/content-type`, единый `content-type` после кроссоверов (уже частично есть). На книгах без дубликатов выигрыш 0; на книгах с N повторами — до `(N-1)×(base64 тела)` минус deflate-окно (дефлятор ZIP видит повторы только в пределах 32KB, а дубликаты обычно в мегабайтах друг от друга — окно их не ловит, так что выигрыш почти полный).

| Критерий | Оценка |
|----------|--------|
| Сложность | 4–7 дней (хеширование в пайплайне, карта `hash→surviving_id`, переписывание `xlink:href`, подсчёт `stats`/`marks` для удалённых тел, тесты: дубли/ссылки/круговая ссылка/разные id один хэш, доки) |
| Риски | Средние: единственный вариант, трогающий семантику документа (ссылки), а не только байты. Нужны инвариантные тесты «все `href` резолвятся», «число уникальных картинок сохранено», «валидность по FB2-схеме». Откат простой: флаг `--no-dedup` |
| Плюсы | Потенциально самый большой выигрыш из трёх (0% обычно, 10–30% на книгах с дубликатами); чистый Python, без новых зависимостей; ускоряет и последующие `ect`/ZIP-проходы (меньше данных) |
| Минусы | Выигрыш бимодален (часто ноль); усложняет учёт `png_saved/jpg_saved` по типам и `program-used` штампы lossy (дубликат штампованного изображения делит судьбу оригинала — решить правилом) |
| Влияние на архитектуру | Умеренное: новый проход между декодированием и `optimize_images`, плюс переписывание ссылок в скелете; `_Image`/статистика расширяются полем `dup_of` |

## Рекомендация

Порядок внедрения по соотношению выигрыш/риск: **3 → 1 → 2**. Дедупликация — единственная с шансом на двузначные проценты и без зависимостей (начать с dry-run счётчика «сколько бы сэкономили», затем включать по умолчанию с `--no-dedup`). PNG-цепочка и JPEG-финиш — опциональные ступени за детектом бинарей, каждая держится правилом «только строго packed-smaller + pixel-identity», поэтому безопасны для дефолта.

## Оценка внешних советов (2026-09-11)

### Картинки: вердикт по пунктам
| Совет | Вердикт | Почему |
|---|---|---|
| Alpha-flatten на белый холст перед анализом | Отклонить (default); идея для `--lossy`, низкий приоритет | Меняет пиксели полупрозрачных областей → нарушает pixel-identity. Проект скипает alpha осознанно (`_has_alpha` → keep) |
| А: бинаризация в 1-bit для сканов | Реализовано: `_lossy_bilevel` (первая ступень `--lossy`, Otsu, SSIM-гейт, retry на полном разрешении) | Дефолту запрещено (порог меняет пиксели) |
| Б: 98% серого → L; JPEG q45–50 | Уже есть в лучшем виде | Проект: точное равенство + метрико-гейтед L-probe. Версия «98%» убьёт цветные 2% (красная буквица станет серой). Фикс-качество без метрики хуже лестницы SSIM |
| В: округление //16 → PNG-8 | Уже есть безопасное; округление — разве что предквант в `--lossy` | Exact-crossover под packed-гейтом покрывает честные случаи; lossy-слияние близких цветов — низкий приоритет |
| Г: бинпоиск качества, SSIM 0.88 | Уже есть и лучше; бинпоиск неверен | Лестница 60→95 вверх вместо бинпоиска — осознанно: качество немонотонно при пережатии (коммент в коде). Порог уже настраивается `--lossy-ssim` |
| Лимиты 1000px/150КБ/80КБ | Отклонить как принцип | Абсолютные капы режут качество независимо от цены байта; 1920px обоснован экранами. Single-export уже делается (один финальный энкод) |

### XML-метаданные (publish-info, src-title-info, history, keywords, stylesheet): отклонить целиком
- Ломает контракт lossless-оптимизатора (сохранение, валидность, «не трогает»).
- Удаление `<program-used>` уничтожит собственный храповик `--lossy` — самоповреждение.
- Удаление stylesheet/history меняет рендеринг и ломает библиотечные менеджеры; экономия — сотни байт, почти в ноль после дефляции.
- Regex-подход — то, чего проект избегает осознанно.
